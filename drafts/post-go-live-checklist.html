Performance Validation on Production CDN
Re-run Lighthouse immediately after DNS cutover — CDN layers can hurt scores
Immediate
🚨
Do not assume the pre-live score carries over. Introducing a CDN between the visitor and your .aem.live origin can drop your Lighthouse score significantly due to HTTP/1.1, injected scripts, or misconfigured caching. You must re-test on the production domain immediately after go-live.
  1. 1
    Run PageSpeed Insights on the PRODUCTION domain — Mobile

    Open pagespeed.web.dev and test your live URL:

    https://www.yourdomain.com/ ← test this https://main--{repo}--{org}.aem.live/ ← compare against this

    Both should score 100. If the production domain scores lower, the gap is caused by the CDN layer.

    📊 PSI — Production Domain vs .aem.live Origin Comparison Insert side-by-side screenshots of PSI results for your production domain and the .aem.live origin. Any score difference highlights CDN-related issues.
  2. 2
    Run PageSpeed Insights — Desktop

    Repeat the comparison on the Desktop tab.

  3. 3
    Diagnose CDN performance issues

    If the production CDN score is lower than the .aem.live origin, check for these common causes:

    Symptom in PSILikely CDN causeFix
    High TTFB (Time to First Byte) CDN running HTTP/1.1 to origin instead of HTTP/2 Enable HTTP/2 or HTTP/3 on the CDN-to-origin connection
    Extra blocking scripts CDN is injecting JS (bot detection, analytics SDKs, RUM) Disable or move CDN-injected scripts; ensure they don't run before LCP
    Cache MISS on every request CDN not honouring origin Cache-Control headers Enable "respect origin cache headers" in CDN config
    Large render-blocking requests WAF or DDoS tools adding latency Tune WAF rules; test by temporarily disabling and re-measuring
    Redirect chain on first load www → apex or HTTP → HTTPS redirect not handled at CDN edge Resolve redirects at CDN edge (not at origin) to avoid extra round-trips
  4. 4
    Validate CDN response headers

    Check that the CDN is not suppressing or overriding important headers:

    curl -I https://www.yourdomain.com/ # Expected headers: # content-type: text/html; charset=utf-8 # cache-control: max-age=3600 ← origin TTL respected # x-push-invalidation: enabled ← opt-in header present # age: 0 ← or a small positive number
    🔍 curl -I Response Headers — Production Domain Insert a screenshot of the curl -I output for your production domain. Highlight cache-control and age headers.
  5. 5
    Check HTTP protocol version
    curl -I --http2 https://www.yourdomain.com/ # First line should read: HTTP/2 200 # If you see HTTP/1.1 200 — upgrade the CDN connection protocol
2
Martech & Analytics Validation on Production
Confirm all tags fire correctly under the production hostname
Within 1 hour
⚠️
Many martech tags are hostname-restricted — they work on staging.yourdomain.com but not www.yourdomain.com, or vice versa. Production is the first time the real hostname is used, so test thoroughly.
  1. 1
    Verify analytics hits on the production hostname

    Open your analytics platform (Google Analytics 4, Adobe Analytics, etc.) real-time report. Browse 3–5 pages on https://www.yourdomain.com/ and confirm:

    • Pageviews appear in the real-time dashboard
    • The hostname shows as www.yourdomain.com, not main--{repo}--{org}.aem.live
    • Events (clicks, scrolls, conversions) fire as expected
    📈 Analytics Real-Time Dashboard — Post Go-Live Insert a screenshot of your analytics real-time view showing active users on the production domain.
  2. 2
    Use Chrome DevTools Network tab to confirm tag firing

    Open DevTools (F12) → Network tab → filter by your analytics domain. Load several pages and confirm network requests are sent:

    🌐 DevTools Network — Analytics Requests on Production Insert a screenshot showing analytics/tag requests in the Network tab. Filter by "collect", "beacon", or your analytics domain name.
  3. 3
    Check tag manager rules use correct hostname

    Open your tag manager (GTM, Adobe Launch, Tealium). Check that all publish rules and triggers that reference a hostname or domain are updated to match the production domain:

    # Bad — domain-specific rule that might not fire on production Condition: hostname equals "staging.yourdomain.com" # Good — use a condition that matches all valid hostnames Condition: hostname contains "yourdomain.com"
  4. 4
    Validate consent management

    If you have a cookie consent banner (OneTrust, Cookiebot, etc.), confirm it:

    • Appears on first visit in all regions where required (e.g., EU/GDPR)
    • Blocks analytics and tracking until consent is given
    • After consent is given, delayed.js loads the analytics scripts correctly
  5. 5
    Test bottom-of-funnel conversion events

    Submit a test form, complete a test transaction, or trigger a key conversion event. Verify it appears in the backend system (CRM, order management, etc.) and in analytics. These events are not affected by the loading sequence change and should remain flat.

Google Search Console — Setup & Monitoring
Submit your sitemap, request indexing, and monitor crawl health
Day 1 onwards
  1. 1
    Verify domain ownership in Search Console

    Go to Google Search Console → Add property → choose Domain (recommended, covers all subdomains and protocols).

    Verify via DNS TXT record — add the record your DNS provider:

    Type: TXT Name: @ (or yourdomain.com) Value: google-site-verification=XXXXXXXXXXXXX
    🔑 Google Search Console — Domain Verification Insert a screenshot of the Search Console domain verification step. After adding the DNS TXT record, click Verify.
  2. 2
    Submit your sitemap

    In Search Console → Sitemaps → add your sitemap URL:

    https://www.yourdomain.com/sitemap.xml

    Click Submit. The status will initially show as Pending — Google typically processes new sitemaps within 24–48 hours.

    🗺️ Search Console — Sitemaps Section Insert a screenshot of the Sitemaps section in Search Console. After submission, it should show the sitemap URL with status "Success" and a count of discovered URLs.
  3. 3
    Request indexing for your most important pages

    In Search Console → use the URL Inspection tool. Enter your homepage URL, click Request Indexing. Repeat for your 5–10 most important pages (home, key product/service pages, contact).

    🔎 URL Inspection Tool — Request Indexing Insert a screenshot of the URL Inspection tool showing "URL is on Google" or the Request Indexing button.
  4. 4
    Monitor key Search Console reports (Week 1+)
    ReportWhere to find itWhat to check
    Coverage / Indexing Indexing → Pages Confirm pages are indexed. Fix any "Crawled - not indexed" or "Soft 404" issues.
    Performance Search results Monitor total clicks and impressions. Expect a dip during re-indexing, then recovery.
    Core Web Vitals Experience → Core Web Vitals Confirm all URLs are in "Good" range once field data accumulates (takes 28 days).
    Links Links → Top linked pages Verify important backlinks still resolve correctly (no 404s).
    Crawl stats Settings → Crawl stats Check for crawl errors or Googlebot being blocked.
    📉 Search Console — Performance Report Insert a screenshot of the Search Console Performance report. Monitor total clicks and impressions trend over the first 4 weeks post go-live.
  5. 5
    Check for crawl errors

    Go to Search Console → Settings → Crawl stats. Review the "Crawl requests breakdown" for any spikes in 404s or server errors in the days after launch.

    🕷️ Search Console — Crawl Stats Insert a screenshot of the Crawl Stats page. Look for any response code other than 200 in the breakdown chart.
4
404 Report — Find & Fix Broken URLs
After migration there will always be 404s. Catch them fast and redirect.
Day 1 onwards
ℹ️
404s are inevitable after a site migration. The goal is not zero 404s on day one — it is fast detection and rapid redirection so users (and search engines) are not left stranded.
  1. 1
    Source 1: Operational Telemetry (RUM) / AEM Slack Bot

    AEM's built-in RUM automatically tracks 404 events from real visitors. Your project's Slack bot (if configured) sends regular 404 reports. Check your project Slack channel for messages like:

    # Example Slack bot 404 report 404 Not Found report for www.yourdomain.com (last 24h): /old-product-page → 142 hits /legacy/category/item → 87 hits /images/old-banner.jpg → 34 hits

    These are your highest-priority redirects to add to the redirects spreadsheet.

  2. 2
    Source 2: Google Analytics — 404 page report

    In GA4, create a custom report or use Explore to find pages with the page title matching your 404 page title:

    # GA4 Explore — Free form report Dimension: Page title → filter: contains "404" or "Not Found" Dimension: Page path Metric: Views Date range: Last 7 days
    🔴 GA4 — 404 Page Report Insert a screenshot of the GA4 Explore or custom report showing 404 page paths sorted by view count. These are the URLs you need to redirect.
  3. 3
    Source 3: Google Search Console — Not Found errors

    In Search Console → Indexing → Pages → filter by "Not found (404)". This shows URLs Google has tried to crawl but received a 404 response for.

    🚫 Search Console — Not Found (404) Pages Insert a screenshot of the Search Console Pages report filtered to "Not found (404)". Export the list and add the high-traffic URLs to your redirects spreadsheet.
  4. 4
    Add missing redirects to the redirects spreadsheet

    For each high-traffic 404, determine the best redirect target and add a row to redirects.xlsx (or Google Drive redirects sheet):

    Source (404 path)Destination (new URL)
    /old-product-page/products/new-product-name
    /legacy/category/item/category/item
    ⚠️
    Avoid redirecting 404 pages to the homepage. This creates "soft 404s" that Google penalises. Always redirect to the most relevant replacement page.
  5. 5
    Preview and publish the updated redirects

    Use AEM Sidekick to preview the redirects spreadsheet, verify the new rows, then publish. Test the redirect works:

    curl -I https://www.yourdomain.com/old-product-page # Expected: HTTP/2 301 # Location: https://www.yourdomain.com/products/new-product-name
  6. 6
    Monitor 404s weekly for the first 4 weeks

    Set a recurring calendar reminder to review 404 reports every week for the first month. The volume should decline as you catch and redirect the long tail of broken URLs.

5
Core Web Vitals Field Data (RUM)
Lab scores are a proxy — field data from real visitors is the ultimate judge
Week 1+
ℹ️
Google's CrUX (Chrome User Experience Report) data takes 28 days to reflect a site change. Check RUM data for early field signals while waiting for CrUX to update.
🎨
LCP
< 2.5 s
Largest Contentful Paint — hero image/text visible
👆
INP
< 200 ms
Interaction to Next Paint — click responsiveness
📐
CLS
< 0.1
Cumulative Layout Shift — visual stability
⚡
TTFB
< 800 ms
Time to First Byte — server response speed
  1. 1
    Check AEM RUM Dashboard

    AEM's Operational Telemetry data is collected automatically from real visitors. Access the dashboard provided by your Adobe account team and check field LCP, INP, and CLS values are within the "Good" thresholds above.

  2. 2
    Check CrUX data via Search Console

    After 28 days, go to Search Console → Experience → Core Web Vitals. Review the URL groups flagged as "Poor" or "Needs improvement". Each group links to the specific URLs and the metric causing the issue.

    📊 Search Console — Core Web Vitals Report Insert a screenshot of the Search Console Core Web Vitals report. Target: all URLs in the "Good" (green) category for both mobile and desktop.
  3. 3
    Run CrUX API check for field data
    # Quick CrUX field data lookup (replace with your domain) curl -s "https://chromeuxreport.googleapis.com/v1/records:queryRecord?key=YOUR_API_KEY" \ -H "Content-Type: application/json" \ -d '{"url": "https://www.yourdomain.com/", "formFactor": "PHONE"}' \ | jq '.record.metrics | {lcp: .largest_contentful_paint.percentiles.p75, inp: .interaction_to_next_paint.percentiles.p75, cls: .cumulative_layout_shift.percentiles.p75}'
  4. 4
    Compare before/after if OpTel was set up pre-launch

    If you instrumented the old site with OpTel before migration, compare the RUM CWV metrics from the old site vs the new AEM EDS site. Document the improvement for stakeholders.

6
Verify Search Engine Indexing
Confirm Google can discover, crawl, and index your pages correctly
Week 1+
  1. 1
    Check indexed page count with a Google site: search

    In a Google search bar, type:

    site:www.yourdomain.com

    Google will show how many pages it has indexed. Compare this to the number of URLs in your sitemap. A large discrepancy (e.g., sitemap has 500 pages but Google only shows 50) indicates an indexing problem.

    🔍 Google — site: Search Result Insert a screenshot of the Google search results for site:www.yourdomain.com. Note the approximate result count shown at the top.
  2. 2
    Check Search Console Indexing → Pages report

    In Search Console → Indexing → Pages, review the breakdown by reason:

    StatusMeaningAction
    IndexedPage is indexed ✅No action needed
    Crawled — not indexedGoogle crawled but chose not to indexCheck for thin/duplicate content or noindex tags
    Discovered — not crawledIn queue, not yet crawledWait or request indexing via URL Inspection
    Not found (404)URL returns 404Add a redirect or fix the URL
    Soft 404Page returns 200 but looks like a 404Fix the page content or add a redirect
    Blocked by robots.txtrobots.txt Disallow rule foundCheck robots.txt — allow if page should be indexed
    Excluded by noindex tagrobots meta tag has noindexRemove noindex if page should be indexed
  3. 3
    Confirm noindex pages are NOT indexed

    For pages you deliberately excluded (e.g., internal tools, draft pages), do a Google site: search for those specific URLs to confirm they do not appear:

    site:www.yourdomain.com/internal-draft-page

    If a noindex page appears, check that the robots metadata was published correctly and Google has re-crawled it since.

  4. 4
    Validate the AEM query index is complete

    The AEM query index powers both the sitemap and client-side search/filtering. Confirm all pages are indexed:

    # Check the query index JSON curl https://www.yourdomain.com/query-index.json | jq '.total' # Compare with sitemap count curl -s https://www.yourdomain.com/sitemap.xml | grep -c '<loc>'

    The counts should be similar (excluding noindex pages).

7
Re-test Push Invalidation on Production
Confirm content changes reach visitors instantly on the live domain
Immediate
  1. 1
    Make a small, visible change on a production page

    In SharePoint or Google Drive, change a visible piece of text on your homepage (e.g., add "(Updated)" to a heading). Make a note of the exact change.

  2. 2
    Publish the change via Sidekick

    Open AEM Sidekick on the page → click Preview → then click Publish. Note the exact time you click Publish.

  3. 3
    Verify the change appears on the production domain

    Within 10–30 seconds, open the production URL in an incognito window (to bypass browser cache):

    https://www.yourdomain.com/

    The change you made should be visible. If it is not visible within 60 seconds, cache invalidation is not working.

  4. 4
    Verify via response headers
    curl -I https://www.yourdomain.com/ # Fresh response from purge: # age: 0 or x-cache: MISS
    🔄 Production CDN — Fresh Response After Publish Insert a screenshot of curl -I output after publishing a change. The Age header should be 0 or very low.
  5. 5
    Undo the test change

    Remove the "(Updated)" text from the heading, preview and republish the page to restore it to its original state.

Ongoing Monitoring Schedule
What to check and how often in the weeks after go-live
Ongoing
Frequency What to Check Tool / Where What "Good" Looks Like
Daily (Week 1) 404 reports from Slack bot / RUM Project Slack channel or AEM RUM dashboard Volume decreasing day-on-day as redirects are added
Daily (Week 1) Analytics real-time data Google Analytics / Adobe Analytics Sessions tracking correctly, no data gaps
Weekly Search Console Performance search.google.com/search-console → Performance Impressions and clicks recovering to pre-launch baseline
Weekly Search Console Indexing → Pages Search Console → Indexing → Pages Indexed page count growing, errors declining
Weekly PageSpeed Insights on production pagespeed.web.dev Lighthouse score stays at 100 — no regressions from code changes
Weekly 404 report — Search Console Indexing → Pages → filter "Not found (404)" All high-traffic 404s have redirects; list shrinking
After 28 days Core Web Vitals — CrUX field data Search Console → Experience → CWV All URLs in "Good" range for LCP, INP, CLS
Monthly Backlinks and linked pages Search Console → Links High-value backlinks resolving to 200 (not 404 or redirect)
Each PR/deploy PSI via AEM GitHub bot GitHub PR checks All checks passing; PSI score 100
✅
Tip: Set up Google Search Console email alerts for critical issues (coverage errors, manual actions, security issues) so you are notified automatically without having to check manually. Settings → Email preferences → turn on "All issues".
  1. 1
    Enable Search Console email alerts

    Search Console → Settings → Notifications → turn on email alerts for:

    • Issues found / fixed in Coverage
    • Manual actions
    • Security issues
  2. 2
    Add your site to a Lighthouse CI monitoring tool

    For ongoing Lighthouse regression prevention, consider setting up Lighthouse CI or a third-party uptime/perf monitor (e.g., Calibre, SpeedCurve) that runs PSI weekly against your key pages.

  3. 3
    Run a post-launch retrospective (2 weeks after go-live)

    Bring together the development team, analytics team, and business stakeholders to review:

    • Performance comparison: before vs after (CWV, PSI)
    • SEO status: indexing progress, organic traffic trend
    • 404s resolved vs outstanding
    • Analytics data quality confirmation
    • Any user-reported issues

Post Go-Live Quick Reference Checklist

  • ☐ PSI score is 100 on the production domain (not just .aem.live) — both mobile and desktop
  • ☐ CDN response headers confirmed — HTTP/2, correct Cache-Control, Age: 0 on fresh pages
  • ☐ Analytics firing on production hostname — real-time data visible in dashboard
  • ☐ Tag manager rules updated for production hostname
  • ☐ Consent management working — tracking blocked until consent given
  • ☐ Google Search Console property verified for production domain
  • ☐ Sitemap submitted to Search Console — status: Success
  • ☐ Key pages requested for indexing via URL Inspection tool
  • ☐ 404 monitoring active — Slack bot or GA4 report configured
  • ☐ First 404 redirect batch added and published
  • ☐ Push invalidation tested on production — change visible within 30s
  • ☐ Search Console email alerts turned on
  • ☐ Weekly monitoring schedule in place (PSI, GSC, 404s, analytics)
  • ☐ 28-day CWV field data review scheduled in calendar
