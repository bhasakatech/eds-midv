1
Content & Design QA
Verify every page looks and behaves correctly on the preview environment
  1. 1
    Open your feature preview URL

    Construct the URL using your branch, repo, and org:

    https://{branch}--{repo}--{owner}.aem.page/

    Example: https://main--eds-events-gehealthcare--gehealthcare.aem.page/

  2. 2
    Cross-browser & responsive check

    Test in Chrome, Firefox, Safari and Edge at mobile (375px), tablet (768px), and desktop (1280px) widths.

  3. 3
    Accessibility audit (WCAG 2.1 AA)

    Run the Chrome DevTools Accessibility panel or Axe extension. Check for:

    • Correct heading hierarchy (H1 → H2 → H3)
    • All images have meaningful alt text
    • Interactive elements have focus styles and ARIA labels
    • Colour contrast ratio ≥ 4.5:1 for body text
  4. 4
    SEO meta tags

    Inspect the page source (Ctrl+U) and confirm each page has:

    <title>Descriptive Page Title | Brand</title> <meta name="description" content="..." /> <meta property="og:title" content="..." /> <meta property="og:image" content="..." />
  5. 5
    Inspect raw HTML from the dev server

    Use curl to see exactly what AEM delivers:

    curl http://localhost:3000/path/to/page.plain.html

    Confirm all canonical content is in the initial HTML payload — not fetched by JavaScript after the fact.

Performance Validation — Lighthouse Score 100
Every page must score 100 on Google PageSpeed Insights (mobile + desktop)
⚠️
Mandatory requirement. The AEM GitHub bot will automatically fail your PR if the PageSpeed score drops below 100. Test on the preview URL (.aem.page), not localhost.
  1. 1
    Run PageSpeed Insights — Mobile

    Go to Google PageSpeed Insights and paste your preview URL:

    https://pagespeed.web.dev/

    Select Mobile tab first — mobile scores are harder to achieve and are what the AEM bot checks.

    📊 PageSpeed Insights — Mobile Result Insert a screenshot of the PSI result here. Target: all four scores at 100 (Performance, Accessibility, Best Practices, SEO).
  2. 2
    Run PageSpeed Insights — Desktop

    Switch to the Desktop tab and re-run.

    🖥️ PageSpeed Insights — Desktop Result Insert a screenshot of the desktop PSI result here.
  3. 3
    Check Core Web Vitals targets
    MetricTarget (Good)What it measures
    LCP — Largest Contentful Paint< 2.5 sWhen the hero image/text is visible
    INP — Interaction to Next Paint< 200 msResponsiveness to user clicks
    CLS — Cumulative Layout Shift< 0.1Visual stability — no jumping elements
  4. 4
    Common fixes if score is below 100
    • LCP too slow: Keep the total network payload before LCP under 100 KB. Move non-critical code to the lazy or delayed phase.
    • CLS: Reserve space for images using explicit width/height attributes. Don't load fonts before LCP.
    • TBT/INP: Move third-party scripts (analytics, chat, tag managers) to the delayed.js phase — triggered ≥ 3 s after LCP.
    • Second origin before LCP: Never connect to a second host before the LCP event. Combine resources on the same origin.
    • Avoid preload/fetchpriority: Adding <link rel="preload"> or fetchpriority="high" actually harms PSI scores in AEM EDS.
  5. 5
    Validate via the AEM GitHub PR check

    When you open a Pull Request, the AEM bot runs PSI automatically using the URL in your PR description. Check the status with:

    gh pr checks
    ✅ GitHub PR Checks — AEM Lighthouse Bot Insert a screenshot of the passing PR checks here. All checks should be green.
3
Analytics & Martech Validation
Confirm all tracking tags fire correctly on the preview environment
ℹ️
After a go-live, analytics baselines for pageviews, bounce rate, and time-on-page will change due to the new loading sequence. This is expected and normal. Align with your analytics team before launch.
  1. 1
    Open Chrome DevTools → Network tab

    Filter by the analytics domain (e.g., google-analytics.com, adobedtm.com). Reload the page and confirm tracking requests fire.

    🌐 Network Tab — Analytics Requests Insert a screenshot showing analytics network requests being made during page load.
  2. 2
    Verify in your analytics dashboard

    Open your analytics platform (Google Analytics, Adobe Analytics, etc.) real-time report. Browse several pages on the preview URL and confirm visits appear within 30–60 seconds.

  3. 3
    Verify martech loads in the Delayed phase

    Analytics, tag managers, consent banners and chat widgets must be loaded in scripts/delayed.js — not in the eager or lazy phase. Open DevTools → Performance and confirm heavy third-party scripts only start after the LCP event.

  4. 4
    Confirm bottom-of-funnel events are unchanged

    Form submissions, transactions and checkout events are captured by server-side systems. Verify these are unaffected by the new loading sequence by submitting a test form and checking the CRM or backend.

  5. 5
    Brief your analytics team

    Share the expected baseline shift with the corresponding analysts. Document which metrics you expect to increase or decrease and why, so the team is not alarmed by the changes post-launch.

4
Operational Telemetry (OpTel)
Instrument your site before launch for before/after performance comparison
  1. 1
    What is OpTel?

    AEM's built-in Real Use Monitoring (RUM) collects Core Web Vitals from real visitors in the field. It is lightweight, privacy-safe, and already bundled with AEM boilerplate. Adding it to your existing pre-migration site early gives you a baseline to compare against after go-live.

  2. 2
    Verify RUM is active

    Open the browser console on your preview URL. You should see no RUM-related errors. Alternatively, use the AEM RUM Dashboard available to your project team.

  3. 3
    Instrument the existing site (if migrating)

    Add OpTel to the old site as early as possible before migration. This lets you measure CWV in the field before the switch and compare with post-launch field data.

5
Legacy Redirects Validation
Map all retired URLs to new destinations before going live
  1. 1
    Find high-impact legacy URLs using Google Search Console

    Open Google Search Console → Links → Top linked pages. Export the list and identify any URLs that will no longer exist after migration.

    🔗 Google Search Console — Top Linked Pages Insert a screenshot of the Search Console Links report. These are the URLs you must redirect.
  2. 2
    Create the redirects spreadsheet

    In the root of your SharePoint / Google Drive project folder, create a file named redirects.xlsx (SharePoint) or redirects sheet (Google Drive) with exactly two columns:

    SourceDestination
    /old-page-url/new-page-url
    /legacy/product-name/products/product-name
    /outdated-pathhttps://other-domain.com/page
    ℹ️
    Source is always a relative path (no domain). Destination can be relative or a full URL for cross-domain redirects.
  3. 3
    Multiple worksheets? Use the right sheet name

    If your spreadsheet has multiple sheets, redirects only work on the sheet named helix-default. Rename your sheet accordingly.

  4. 4
    Preview and test redirects

    Use AEM Sidekick to publish the redirects spreadsheet to the preview environment. Then test each redirect:

    # Test a redirect (should return HTTP 301) curl -I https://{branch}--{repo}--{owner}.aem.page/old-page-url

    Look for HTTP/2 301 and a Location: header pointing to the new URL.

  5. 5
    Wildcard redirects (CDN-level only)

    If you need to redirect an entire path pattern (e.g., all /old-section/* pages), configure these at the CDN layer — they are not supported in the redirects spreadsheet. Example pattern:

    Input: /old-section/* Redirect to: /new-section/$1
    ⚠️
    Wildcard redirects can create 301 → 404 chains. Only use them when individual URL mapping is impractical. Always check your CDN vendor's documentation for the exact syntax.

Sitemap & robots.txt
Help search engines discover and crawl your pages correctly
✅
AEM Edge Delivery Services generates a sitemap automatically from the query index each time you publish a page. You do not need to build it manually.
  1. 1
    Verify the sitemap is generated

    Open the sitemap URL on your preview domain:

    https://{branch}--{repo}--{owner}.aem.page/sitemap.xml

    You should see an XML file listing all published pages.

    🗺️ sitemap.xml — Browser View Insert a screenshot of the sitemap.xml file rendered in the browser. Verify it lists your pages with correct <loc> entries.
  2. 2
    Exclude specific pages from the sitemap (noindex)

    To keep a page out of the sitemap AND prevent search engines from indexing it, set the robots metadata on that page to noindex.

    In SharePoint / Google Drive page metadata:

    PropertyValue
    robotsnoindex

    AEM's sitemap automatically skips pages where the robots column contains noindex. This works as long as a robots column exists in the query index.

    ℹ️
    Excluding 30 pages from 100: Add robots: noindex metadata to each of the 30 pages you want hidden. After publishing, the sitemap will only list the remaining 70 pages. The pages are still accessible by direct URL — they are just not surfaced to search engines.
  3. 3
    Add hreflang for multilingual sites

    For sites targeting multiple regions/languages, add hreflang entries to the sitemap. This prevents duplicate content penalties across language versions. Configure this via your sitemap settings in the AEM configuration service.

  4. 4
    Configure robots.txt

    Add a custom robots.txt via the AEM Configuration Service. A good default that allows all crawlers and references your sitemap:

    User-agent: * Allow: / Sitemap: https://www.yourdomain.com/sitemap.xml
    ⚠️
    Important: robots.txt is case-sensitive. Use exact paths. Note: adding Disallow: to a URL does NOT remove it from Google's index — it only restricts crawling. To properly remove a URL, use Allow + a noindex meta tag on that page.
  5. 5
    Block pages from crawlers without removing them (robots meta tag)

    If you have pages that should be accessible via direct link but not indexed by Google:

    <!-- Add to the page metadata in SharePoint / Google Drive --> robots: noindex, nofollow

    This renders as a <meta name="robots" content="noindex, nofollow"> tag in the page HTML. AEM reads this tag both for the sitemap exclusion and for the query index.

  6. 6
    Verify robots.txt is accessible
    curl https://www.yourdomain.com/robots.txt

    Confirm it returns the correct content and references your sitemap URL.

    🤖 robots.txt — Curl Output Insert a screenshot or copy of the robots.txt curl response here. Verify the Sitemap line points to the correct production URL.

Canonical URL Validation
All canonical URLs must return HTTP 2xx — no 3xx or 4xx
  1. 1
    What is a canonical URL?

    A canonical URL is the preferred version of a page. It is declared in the <head> as:

    <link rel="canonical" href="https://www.yourdomain.com/the-page" />

    If the canonical URL returns a redirect (3xx) or error (4xx), Google may not correctly index your page, leading to duplicate content issues.

  2. 2
    Extract all canonical URLs from your pages

    Run a crawl using Screaming Frog SEO Spider (free up to 500 URLs), or extract manually from the sitemap:

    # Fetch the sitemap and extract all URLs curl -s https://{branch}--{repo}--{owner}.aem.page/sitemap.xml \ | grep -o '<loc>[^<]*</loc>' \ | sed 's/<loc>//g;s/<\/loc>//g'
  3. 3
    Test each canonical URL returns HTTP 200
    # Check HTTP status code for a URL curl -o /dev/null -s -w "%{http_code}" https://www.yourdomain.com/the-page # Bulk check all URLs in a list file while IFS= read -r url; do status=$(curl -o /dev/null -s -w "%{http_code}" "$url") echo "$status $url" done < urls.txt

    Every URL must return 200. Any 301, 302, or 404 must be fixed before go-live.

  4. 4
    Common canonical issues to fix
    IssueFix
    www vs non-www mismatchAdd a redirect from the non-canonical version to the canonical. Configure in CDN or redirects sheet.
    Trailing slash inconsistencyPick one convention (with or without slash) and redirect all variants to it.
    HTTP vs HTTPSHTTPS is mandatory in AEM EDS. Ensure all canonical URLs use HTTPS.

Favicon
Add a site icon so it appears in browser tabs and bookmarks
  1. 1
    Add the favicon to the repository

    Place your favicon in the project root or the icons/ folder and commit it:

    /favicon.ico ← standard browser fallback (32×32 px) /favicon.png ← modern browsers (recommended, 32×32 or 48×48 px)
  2. 2
    Reference the favicon in head.html

    Open head.html and add:

    <link rel="icon" type="image/png" href="/favicon.png" /> <link rel="shortcut icon" href="/favicon.ico" />
  3. 3
    Verify in the browser

    Open the preview URL. The favicon should appear in the browser tab. If it does not, hard-refresh with Ctrl+Shift+R.

    🔖 Browser Tab — Favicon Visible Insert a screenshot of the browser tab showing the site favicon.

Author Authentication
Control who can preview and publish content via the AEM Sidekick
ℹ️
By default, authentication is not required for the AEM Sidekick. This step is only needed if you want to restrict preview/publish access to specific users or domains.
  1. 1
    Decide your access model
    OptionWhen to use
    Open (default)Anyone with the URL can preview; suitable for low-security marketing sites
    Domain-restrictedOnly users with *@yourcompany.com email can preview
    Individual user listExact email addresses are granted publish rights
  2. 2
    Configure access via the Admin API (domain-wide example)
    curl -X POST https://admin.hlx.page/config/{org}/sites/{site}/access/admin.json \ -H "content-type: application/json" \ -H "x-auth-token: <your-auth-token>" \ --data '{ "role": { "author": [ "*@yourcompany.com" ], "publish": [ "admin.user@yourcompany.com" ] } }'
    ℹ️
    Get your x-auth-token from the browser Network tab — copy it from any authenticated Sidekick request to admin.hlx.page.
  3. 3
    Test the Sidekick login flow

    After setting the access config, open Sidekick on a page. You should see a Sign In button. Click it and authenticate with your Microsoft (SharePoint) or Google (Drive) account.

    🔐 AEM Sidekick — Sign In Button Insert a screenshot of the Sidekick showing the Sign In option after authentication is enabled.
  4. 4
    Grant Azure AD admin consent (SharePoint only)

    If using SharePoint, an Azure AD admin must grant consent for the AEM Content Integration Admin API. Steps:

    • Go to Azure Portal → Active Directory → Enterprise Applications
    • Search for AEM Content Integration Admin API
    • Select Permissions tab → click Grant admin consent for {organization}
    🏢 Azure Portal — Grant Admin Consent Insert a screenshot of the Azure Portal Enterprise Applications permissions tab.

CDN Configuration
Point your production CDN to the main branch .aem.live origin
🚨
Always use the main branch for production. Your CDN origin must start with main--. Using a feature branch in production disables caching and push invalidation.
  1. 1
    Choose your CDN option
    OptionWho uses it
    Adobe Managed CDNIncluded in your AEM Sites license. Zero CDN management overhead.
    BYO CDN (Fastly, Akamai, Cloudflare, CloudFront)You already have a CDN contract and want to keep using it.
  2. 2
    Required CDN settings (BYO CDN)
    SettingRequired Value
    Origin URLhttps://main--{repo}--{org}.aem.live
    X-Forwarded-Host headerYour production domain (e.g., www.yourdomain.com)
    X-Push-Invalidation headerenabled
    Compressiongzip enabled
    Query parametersForward to origin + include in cache key
    Age response headerSuppress or set to 0
    Origin cache controlHonour origin Cache-Control headers
  3. 3
    Adobe Managed CDN — DNS setup

    Set your DNS records as follows:

    # www subdomain — CNAME record www.yourdomain.com CNAME cdn.adobeaemcloud.com # Apex domain — A records (for automatic www redirect) yourdomain.com A 151.101.3.10 yourdomain.com A 151.101.67.10 yourdomain.com A 151.101.131.10 yourdomain.com A 151.101.195.10
    ℹ️
    Lower your DNS TTL to 60–300 seconds a day before go-live to speed up the DNS cut-over. Restore it to 3600+ after go-live.
  4. 4
    Test the CDN in staging first

    Configure a staging/test domain pointing to your CDN before updating the production DNS. Verify all of the following on staging:

    • www → apex redirect (or vice versa) works correctly
    • HTTPS certificate is valid
    • Page loads correctly and PSI score is still 100
    • Redirects from the spreadsheet still work
  5. 5
    Validate with a PSI comparison

    After enabling the CDN, run PSI against both URLs and compare:

    # Direct .aem.live origin (reference) https://main--{repo}--{org}.aem.live/ # Through your production CDN https://www.yourdomain.com/

    A drop in score on the CDN URL vs. the origin URL signals CDN misconfiguration (HTTP/1.1, injected scripts, aggressive WAF rules, etc.).

Push Invalidation Setup
Ensure published content changes instantly appear on your production domain
ℹ️
Push invalidation automatically purges your production CDN cache whenever a page is published on the main branch. Without it, visitors may see stale content for hours.
  1. 1
    Understand how push invalidation works

    When an author publishes a page in AEM (via Sidekick), the following happens automatically:

    1. AEM pushes the change to main--{repo}--{org}.aem.live
    2. AEM sends a purge request to your registered CDN
    3. The CDN evicts the stale cache entry for that URL
    4. The next request to your production domain fetches the fresh content
  2. 2
    Register your production CDN in the config service

    Select your CDN vendor and run the appropriate configuration command:

    Adobe Managed CDN:

    curl --request POST \ --url https://admin.hlx.page/config/{org}/sites/{site}/cdn.json \ --header 'content-type: application/json' \ --header 'x-auth-token: <your-auth-token>' \ --data '{ "prod": { "host": "www.yourdomain.com", "type": "managed" } }'

    Cloudflare:

    curl --request POST \ --url https://admin.hlx.page/config/{org}/sites/{site}/cdn.json \ --header 'content-type: application/json' \ --header 'x-auth-token: <your-auth-token>' \ --data '{ "prod": { "host": "www.yourdomain.com", "type": "cloudflare", "cloudflare": { "zoneId": "<your-cloudflare-zone-id>", "apiToken": "<your-cloudflare-purge-token>" } } }'

    For Fastly, Akamai, and CloudFront — refer to the vendor-specific docs linked in the References section.

  3. 3
    Add the opt-in header to your CDN configuration

    Your CDN must send this header to the AEM origin to enable long cache TTLs and push invalidation:

    X-Push-Invalidation: enabled

    Configure this as a request header forwarded from the CDN to the origin.

  4. 4
    Test push invalidation end-to-end
    1. Make a small, visible change to a page (e.g., change a heading in SharePoint/Google Drive)
    2. Use AEM Sidekick to Preview the change, then Publish it
    3. Within 10–30 seconds, visit the production URL: https://www.yourdomain.com/the-page
    4. Confirm the change is visible
    5. Check the response headers to confirm the cache was purged:
    curl -I https://www.yourdomain.com/the-page # Look for: Age: 0 (fresh response, not from cache) # Or: X-Cache: MISS (cache was purged and refetched)
    🔄 Push Invalidation — Response Headers Insert a screenshot of the curl -I output showing Age: 0 or X-Cache: MISS after publishing a change.
  5. 5
    Troubleshoot if invalidation does not work
    SymptomLikely causeFix
    Old content shown after publishX-Push-Invalidation header not forwardedAdd header in CDN config
    Purge requests failingInvalid API token / wrong zone IDRe-run the config POST with correct credentials
    Invalidation not triggeredOrigin URL does not start with main--Update CDN origin to main--{repo}--{org}.aem.live

Notify Adobe Engineering
Let the Edge Delivery Services team know your go-live date so they can monitor
  1. 1
    Send a go-live notification email

    Email aemgolives@adobe.com at least 48 hours before go-live. Include:

    To: aemgolives@adobe.com Subject: Go-Live Notification — www.yourdomain.com 1. aem.live URL(s): https://main--{repo}--{org}.aem.live/ 2. Production domain: https://www.yourdomain.com 3. Planned go-live: YYYY-MM-DD HH:MM UTC 4. Primary contact: Name, email, phone 5. Teams/Slack channel: #your-project-channel
  2. 2
    Set up a Teams or Slack collaboration channel

    If you do not already have a channel with the Adobe EDS team, refer to the Teams Collaboration guide to create one. This is used for real-time support during go-live.

Final Pre Go-Live Checklist — Quick Reference

  • ☐ Content & design reviewed on preview URL — no visual regressions
  • ☐ Lighthouse score 100 on Mobile AND Desktop (Google PageSpeed Insights)
  • ☐ Analytics tracking confirmed firing on preview environment
  • ☐ Analytics team briefed on expected baseline changes
  • ☐ OpTel / RUM active on the existing site for baseline capture
  • ☐ Redirects spreadsheet populated and tested (all return HTTP 301)
  • ☐ sitemap.xml verified — all live pages listed, noindex pages excluded
  • ☐ robots.txt configured and verified — Sitemap line present
  • ☐ All canonical URLs return HTTP 200 — no 3xx / 4xx
  • ☐ Favicon committed and visible in browser tab
  • ☐ Author authentication configured (or deliberately left open)
  • ☐ CDN tested in staging — PSI score stable
  • ☐ Push invalidation configured and end-to-end tested
  • ☐ Adobe engineering notified via aemgolives@adobe.com
